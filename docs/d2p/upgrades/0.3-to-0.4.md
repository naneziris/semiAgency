# Upgrade 0.3 → 0.4: engagement kinds (proposal / deck / meeting)

What changes: each engagement gets a `kind` that selects which stages and gates apply. Two new prompts (`/write-storylines`, `/summarize-meeting`), two new instruction files (`content.md`, `notes.md`), templates for both, a scenarios guide, and small edits to five existing prompts so they refuse to run on the wrong kind. Scripts need three changes (see step 3).

Nothing in existing engagements breaks: an engagement without `kind` is treated as `proposal`.

## Step 0 — know where you are

```
git status            # commit or stash anything pending
cat VERSION           # missing = 0.3 (VERSION was introduced in 0.4)
```

## Step 1 — apply the scaffold changes (choose one way)

**A. Patch (fastest).** Copy `upgrade-0.3-to-0.4.patch` (shipped next to this file) into the repo root and run:

```
git apply --check upgrade-0.3-to-0.4.patch   # dry run; reports conflicts, changes nothing
git apply upgrade-0.3-to-0.4.patch
```

`--check` fails only if you edited one of the touched files by hand. In that case use B for those files and `git apply --exclude=<path> …` for the rest.

**B. By hand / via Copilot.** Copy these files verbatim from the 0.4 scaffold (all are self-contained):

      .github/instructions/notes.instructions.md

For the "edit" files the safest move is to overwrite with the 0.4 version — you should not have needed to change them locally.

## Step 2 — existing engagements

Add `"kind": "proposal"` to each `engagements/*/state.json` (or let `status.py` default it — see step 3). Nothing else.

## Step 3 — update the scripts (one Copilot prompt)

Paste into Copilot agent mode with `@analyst`:

```
Read docs/d2p/scenarios.md and the updated docs/d2p/bootstrap.md §2 rows for new_engagement.py, status.py, validate.py and followup_agenda.py.
Apply these changes, stdlib only, and keep every existing --selftest passing:
1. new_engagement.py: add --kind proposal|deck|meeting (default proposal), --subject, and --from <dir> (copies inputs/ and normalized/ from another engagement). Write "kind" and "subject" into state.json. Copy only the templates that kind needs (proposal: brief, discovery, options, proposal, storylines, deck, speech, tasks; deck: content, storylines, deck, speech; meeting: notes, tasks).
2. status.py: read kind (missing → "proposal"). Gate map: proposal G1–G5; deck G1,G3,G4; meeting G5. Only list gates and suggest prompts valid for the kind. --pass on a gate not in the map is an error.
3. validate.py: add schemas for content.md (sections; K and F ids unique/sequential; every K/F row cited) and notes.md (sections; "My actions" table shape). deck.json refs may be K/F ids when kind is deck; storylines coverage must list every K id when kind is deck.
4. followup_agenda.py: read open points from discovery.md, content.md or notes.md, whichever exists.
Extend the selftests: create one temp engagement per kind and assert status.py reports the right gate map and validate.py accepts the kind's templates.
Run python scripts/selftest_all.py (or each --selftest) and show me the output.
```
