# Discovery2Presentation (D2P) — System Design (v0.1)

Workflow #1: stakeholder discovery → options → proposal → presentation → team follow-through.
Target tooling: GitHub Copilot (agent mode) in VS Code, Python scripts for everything deterministic, local files only. Built entirely on the corporate machine — see the companion `docs/d2p/bootstrap.md` for the Copilot implementation kit. D2P is workflow #1 of the semiAgency workspace; the other workflows are described in `docs/architecture.md`.

**Environment constraints (corporate Windows machine):** Python is available but **no third-party libraries** can be installed (no python-pptx, openpyxl, lxml); **PowerShell scripts are blocked** (so no Office COM automation); the reference deck is internal-only and never leaves that machine. Every script below is therefore **Python standard library only** — `zipfile`, `xml.etree.ElementTree`, `json`, `re`, `hashlib`, `csv`, `datetime`. Transcripts arrive as `.md`.

---

## 1. Design principles

1. **AI only where judgment is needed.** Anything that is parsing, validating, rendering, diffing, or bookkeeping is a script. The model reads and writes markdown/YAML; it never touches OOXML, xlsx internals, or styling.
2. **Files are the state.** One folder per engagement, with a `kind` (`proposal`, `deck`, `meeting`) that selects which stages and gates apply — see `docs/d2p/scenarios.md`. Every stage produces a file with a fixed schema. `state.json` records which gates you have approved. This is the same "context externalization" you already use in SemiPilotPro — reuse the philosophy, not the code.
3. **Human gates are explicit and few.** Five gates (see §3): facts, option, storyline, visual, tasks. Copilot never advances a stage on its own; a script tells you what the next action is. The gates are the product — they are what makes the deck defensible in front of the people who gave you the facts.
4. **Corporate styling is copied, never generated.** The reference deck's slide master is the single source of truth. No "make it look corporate" prompts.
5. **Scripts never author OOXML from scratch.** They clone XML that PowerPoint itself wrote (slides from your own decks) and replace text. This is what makes a stdlib-only builder safe: the risky part (valid slide XML) is never our code's job.
5. **Traceability by IDs.** Needs get IDs (`N1…`), options `O1…`, proposal claims reference needs, slides reference proposal sections, tasks reference the meeting they came from. Scripts check for orphans; AI doesn't have to be trusted to "cover everything".

## 3. Stages, artifacts, gates

| # | Stage | Trigger | Input | Output | Gate |
|---|-------|---------|-------|--------|------|
| 0 | New engagement | you | name, stakeholder list | folder + `state.json` | – |
| 1 | Discovery prep | before meeting | any prior docs in `inputs/` | `brief.md` (context summary, hypotheses, question guide) | – |
| 2 | Discovery synthesis | after meeting | transcript + notes + docs | `discovery.md` | **G1: facts verified** |
| 3 | Follow-up loop | open questions remain | new transcript/notes | `discovery.md` (merged), `followups/agenda-N.md` + `.ics` | (back to G1) |
| 4 | Options sketch | G1 passed, no blocking questions | `discovery.md` | `options.md` (2–3 approaches) | **G2: option chosen** |
| 5 | Proposal + storylines | G2 | discovery + chosen option | `proposal.md`, `storylines.md` (2 arcs, compared, one recommended) | **G3: proposal facts approved AND storyline chosen** |
| 6 | Deck | G3 | proposal + chosen storyline + brand | `deck.json` → `storyboard.html`, `deck.pptx` | **G4: open in PowerPoint, visual QA** |
| 7 | Speech + dry run | G4 | deck.json + proposal + voice.md | `speech.md` → notes in pptx, timing report, Q&A prep | – |
| 8 | Team brief | after stakeholder presentation | proposal | `team-brief.md` | – |
| 9 | Team follow-through | after team meeting | team meeting transcript/notes | `tasks.json` → appended to `tracker/actions.xlsx` | **G5: tasks approved before append** |

`state.json`:

```json
{
  "engagement": "2026-09-acme-support-bot",
  "stakeholders": ["Maria K. (Ops lead)", "Jan D. (IT)"],
  "stage": 4,
  "gates": {
    "G1": {"passed": true, "at": "2026-09-10", "by": "nikos"},
    "G2": {"passed": true, "chosen_option": "O2"},
    "G3": {"passed": false, "chosen_storyline": null}
  },
  "followups": 2
}
```

`scripts/status.py` reads this and prints: stage, what's blocking, and the exact prompt/script to run next. That is the whole "orchestration" — no rail engine needed at this size.

## 4. Deterministic vs AI — per stage

| Stage | Deterministic (script) | AI (Copilot prompt) | Why the split |
|---|---|---|---|
| 0 | `new_engagement.py` scaffolds folder, templates, state | – | pure bookkeeping |
| 1 | `ingest.py` normalizes any prior docs | `/prep-discovery`: context summary, 3–5 hypotheses, question guide grouped by theme | question quality is judgment |
| 2 | `ingest.py` (`.md` transcript speaker/timestamp normalization; `.docx`/`.pptx` → text via zip+XML; `.pdf` best-effort or via a manual "open in Word → save as .docx" step; manifest with hashes); `validate.py` checks discovery.md schema and ID uniqueness | `/synthesize-discovery`: extract needs, pains, constraints, decisions, open questions, stakeholder map; every item cites source (`[T1 12:34]`, `[doc:roadmap.pdf p3]`) | extraction is AI; citation format and schema are enforced by script so you can verify at G1 quickly |
| 3 | `followup_agenda.py`: open questions → agenda.md + `.ics` invite with agenda in the body; status diff of open questions (resolved/new) | `/merge-followup`: merge new material into discovery.md, mark questions resolved with evidence, never delete verified facts | merge needs judgment; the diff and the invite don't |
| 4 | `validate.py`: exactly 2–3 options, each has required sections, each references ≥1 need ID; orphan-need report | `/sketch-options`: candidate approaches with scope, fit-to-needs matrix, effort band, risks, assumptions, "what we'd need to be true" | this is the thinking step; the coverage check is mechanical |
| 5 | `validate.py`: every proposal section references needs; unresolved blocking questions block this stage; exactly 2 storylines, each covering every H need, one recommended | `/write-proposal` from chosen option writes `proposal.md` **and** `storylines.md` (two narrative arcs over the same proposal, compared, one recommended with reasons); `@critic` reviews against discovery.md for unsupported claims | writing + critique are AI; consistency is checked. Storylines differ in *telling* (problem-first vs. vision-first, decision-first vs. journey), never in *what is proposed* — that was fixed at G2 |
| 6 | `storyboard.py`, `build_deck.py`, `lint_deck.py` (see §5); `validate.py` checks `deck.json` follows the chosen storyline's outline | `/outline-deck`: proposal + chosen storyline → `deck.json`, choosing only component kinds listed in `brand/components.md`, density per `brand/examples/` | AI fills the chosen arc into slides; script owns every pixel |
| 7 | `timing.py` (words → minutes at your measured pace; per-slide and total); notes written into pptx by `build_deck.py` with emphasis markup rendered bold | `/write-speech`: per-slide script using `voice.md`, marks emphasis words `**like this**`; `/critique-deck`: hostile stakeholder Q&A, weakest-slide report | a real dry run stays human; the model can only prepare you |
| 8 | – | `/brief-team`: one-pager for the team meeting: what was heard, what we propose, what we need from the team, decisions required | pure writing |
| 9 | `append_tasks.py`: validates `tasks.json`, dedups by hash(source, action), appends rows to `tracker/actions.xlsx` without touching existing rows/formatting | `/extract-tasks`: from team meeting notes/transcript → owner, action, due, depends-on, source ref | extraction is AI; the tracker write is deterministic and append-only so workflow #3 and #1 share it safely |

Candid notes on the split:

- **Don't let Copilot "run the pipeline".** Each prompt does one step and stops. You already found in SemiPilotPro that mid-execution checkpointing is the weak spot; here the cheapest fix is to never have long executions at all.
- **The `.ics` follow-up invite is the right compromise** with your "no auth plumbing yet" stance: you double-click it, Outlook does the rest. If you later want Graph API, it's one script swap.
- **Stage 7 "dry run" is mostly not automatable.** What you can get: timing, anticipated questions, a critique of the narrative. What you cannot get: the rehearsal itself. Don't over-invest here.
- **Stage 1 is where hallucination risk is highest** (hypotheses before evidence). Keep the brief labelled as hypotheses and make G1 the point where hypotheses either become cited needs or get dropped.

## 5. Corporate look and feel — how to get it from previous decks

Your decks are built on a corporate template, the reference deck can't leave the corporate machine, and no libraries are allowed. That rules out the obvious tooling but not the approach: a `.pptx` is a zip of XML, and the stdlib handles zips and XML. Approaches considered:

| Approach | How | Fidelity | Effort | Verdict |
|---|---|---|---|---|
| **A. Clone exemplar slides, replace text** | Curate 8–15 slides from past decks into `components.pptx` (one per slide *kind*: title, section, bullets, two-column, option comparison, timeline, architecture…). Tag text shapes by *shape name*. Builder copies the slide part + rels + media and swaps the text. | Exact — every byte of styling was written by PowerPoint | Medium once (curation + tagging), then zero | **Do this. It is the only path that is both stdlib-only and exact.** |
| B. Add slides from layouts by writing new slide XML | Author `<p:sld>` with placeholder shapes referencing the layout | Exact if the XML is right | Higher; PowerPoint "repair" dialogs on subtle mistakes; every layout needs its own placeholder mapping | Not needed if A covers all slide kinds. Keep as a later option only for bare layouts. |
| C. Token spec (theme fonts/colors, inventory) | `inspect_components.py` reads `theme1.xml` + component slide names/tags | n/a (metadata) | Low, scripted | **Do this — it's the vocabulary the AI outliner is allowed to use** |
| D. Regenerate styling (pptxgenjs / html→pptx / AI-written OOXML) | Rebuild the look from extracted colors | "Almost corporate" — always slightly off | High, ongoing, and needs libraries anyway | **Reject.** |
| E. Structural few-shot from past decks | `skeletonize_deck.py` dumps each past deck as `title / component-kind / bullet count / has-image` | n/a (informs narrative/density) | Low, scripted, stdlib | **Do this — the "informed by previous presentations" part** |
| F. Office COM via PowerShell / VBA | Drive PowerPoint directly | Exact, plus free PNG previews | Low | **Unavailable** (PowerShell blocked). Re-evaluate if inline `powershell -Command` turns out to be allowed — it would give you slide previews for free. |

**Recommendation: A + C + E.** One mechanism only — *clone and fill*. The builder never creates a shape, never sets a font, never picks a color. It copies a slide PowerPoint saved and edits `<a:t>` text nodes. The ~600 lines of stdlib code this needs are less than the python-pptx surface you'd otherwise depend on, and they are boring code.

### 5.1 One-time calibration (on the corporate machine)

1. Create `brand/components.pptx` from the corporate template. Copy in one clean example of every slide kind you actually use — from your own past decks, so the master, theme, footer and logo come along. Aim for 8–15 slides. Delete any slide you can't imagine reusing.
2. Tag shapes by name — but only the custom ones. Real placeholders (title, subtitle, body) are identifiable in the XML by `<p:ph type=…>` and the inspector auto-detects them, so a plain title+bullets slide needs no work at all. For custom-drawn shapes (comparison cards, timeline steps) open Home → Select → Selection Pane and rename the text shape to `{{col1_head}}`, `{{col1_body}}`, … Name each slide's *kind* with a hidden `{{kind:option-comparison-3col}}` text box or let the inspector derive it from the layout name. Shapes you don't tag are frozen decoration and get cloned verbatim.

   This also answers "can I point at previous decks per run?": for *structure* yes (`skeletonize_deck.py` on any deck → density and slide-count norms); for *styling* no — pixels always come from the calibrated `components.pptx`. There is deliberately no one-shot "notes → deck" prompt: every deck passes G1 (facts), G2 (option), G3 (storyline) with you in the loop.
3. Run `inspect_components.py`. Output `components.md`:

   ```
   ## title-slide            (slide 1)  tags: title, subtitle
   ## section-header         (slide 2)  tags: title
   ## bullets                (slide 3)  tags: title, body        body: up to 6 bullets, 2 levels
   ## two-column             (slide 4)  tags: title, left_head, left_body, right_head, right_body
   ## option-comparison-3col (slide 5)  tags: title, col1_head, col1_body, col2_head, col2_body, col3_head, col3_body
   ## timeline-4             (slide 6)  tags: title, step1..step4, step1_note..step4_note
   theme: major=Segoe UI Semibold, minor=Segoe UI; accent1=#0057B8 …
   ```

   The outliner prompt is told: "use only these kinds; fill only these tags." That is the contract.
4. Run `skeletonize_deck.py` on 2–3 past decks → `brand/examples/*.json` (slide sequence, kind guessed by layout name + shape count, bullet density). Read by `/outline-deck` as examples of how you structure a 20-minute proposal.
5. Write `brand/voice.md` by hand.

Everything lives and is built on the corporate machine, with Copilot writing the scripts there. No dummy template is needed: `components.pptx` *is* the corporate template, so calibration and development are the same step. Use a local `git init` for history anyway — Copilot agent mode occasionally rewrites files you didn't ask it to, and `git diff` is the cheapest safety net.

### 5.2 `deck.json` — the contract between AI and script

```json
{
  "meta": {"title": "Support triage assistant — proposal", "audience": "Ops leadership", "minutes": 20},
  "slides": [
    {"kind": "title-slide",
     "fields": {"title": "Support triage assistant", "subtitle": "Proposal · 15 Sep 2026"}},
    {"kind": "bullets",
     "fields": {"title": "What we heard",
                "body": ["Triage takes 40% of L1 time [N1]",
                         "No visibility of repeat issues [N3]",
                         "  - sub-point at level 2"]},
     "refs": ["N1", "N3"]},
    {"kind": "option-comparison-3col",
     "fields": {"title": "Three ways to approach it",
                "col1_head": "O1 · Rules-based router", "col1_body": ["Cheap", "Brittle"],
                "col2_head": "O2 · Copilot agent (proposed)", "col2_body": ["…"]},
     "refs": ["O1", "O2", "O3"]},
    {"kind": "section-header", "fields": {"title": "Proposal"}}
  ]
}
```

(JSON, not YAML, for every machine-read artifact — YAML parsing isn't in the stdlib and Copilot doesn't care. Markdown stays for the human-read ones.)

`build_deck.py` (stdlib):

- Unzips `components.pptx` into memory. Output starts as a copy of it with **all** slides removed: drop `ppt/slides/*` and `ppt/notesSlides/*` and their `_rels`, remove their `<Override>` entries from `[Content_Types].xml`, empty `<p:sldIdLst>` in `presentation.xml`, drop the matching `Relationship` entries in `presentation.xml.rels`. Masters, layouts, theme, notesMaster and media survive untouched.
- For each `deck.json` slide: copy the component slide's XML and its `.rels` under a new number, re-add the content-type override, append a `<p:sldId id="…" r:id="…">` and the relationship. Media referenced by the slide's rels is kept (it's already in the package; a slide cloned twice shares it).
- Fill tags: find `<p:sp>` whose `<p:cNvPr name="{{tag}}">` matches; for a string value, keep the first `<a:p>`, keep its first `<a:r>`'s `<a:rPr>`, set `<a:t>`, delete the other runs/paragraphs; for a list value, use the first `<a:p>` as a paragraph template and clone it per bullet, setting `lvl` from indentation. Untagged shapes are left alone. Unfilled tags get emptied and reported by lint.
- Notes: clone the component slide's `notesSlide` if it has one (otherwise the first notes slide in the package as template), point its rels at the new slide, write `speech.md` paragraphs for that slide; `**word**` becomes a run with `<a:rPr b="1" u="sng">`.
- Stamps `generated-by: build_deck <hash>` in slide 1's notes.
- Zips back with `ZIP_DEFLATED`, `[Content_Types].xml` first.
- `--selftest` builds a 3-slide deck from `tests/fixtures/mini.pptx` (a 3-slide deck you save once from PowerPoint on the corporate template) and re-parses it. The real proof is opening it in PowerPoint once without a repair prompt; after that, since the code path is identical for every slide kind, it stays valid.

Where this can bite, so you know up front: `<a:fld>` fields (slide numbers/dates) inside tagged shapes — skip runs inside `<a:fld>`; grouped shapes (`<p:grpSp>`) — search recursively; SmartArt and charts — do not tag them, clone verbatim; two components sharing one image is fine, but a component with a *different* master than the rest is not — keep `components.pptx` on one master.

`lint_deck.py` flags: text length vs. the component's original text length (proxy for overflow, calibrated per tag), empty tags, bullets >6 per body, needs never referenced by any slide, slide count outside the range seen in `examples/` for the target duration.

**Previews.** Without LibreOffice or COM there is no automated PNG render. Two substitutes: `storyboard.py` renders `deck.json` to a plain HTML storyboard (kind, title, text, refs) for narrative review before building; and G4 visual QA is you opening `deck.pptx` in PowerPoint. That is fine — you'd open it anyway before presenting.

### 5.3 Editing after generation

Once you hand-edit `deck.pptx`, it's no longer regenerable without losing edits. Rule: edit `deck.json` / `speech.md` and rebuild until G4 passes; after G4, hand-edit the pptx freely and treat the json as history. `build_deck.py` refuses to overwrite a pptx whose notes lack the `generated-by` stamp unless `--force`.

## 6. Copilot mechanics that matter

- **`copilot-instructions.md`** holds the invariants: ID scheme, "never modify `inputs/`", "run `scripts/…` instead of reimplementing", citation format, "stop after one stage".
- **`*.instructions.md` with `applyTo`** keeps stage-specific rules out of the global context; they load only when the matching file is open/edited.
- **Prompt files** take arguments (`/synthesize-discovery engagement=2026-09-acme`) and can reference the instruction files and `brand/*.md` as context. Each prompt ends with "run `python scripts/validate.py <artifact>` and fix any errors it reports" so the deterministic check happens inside the same Copilot turn.
- **Custom agents**: `analyst` (read/edit/terminal) for stages 1–9; `critic` (read-only) for the review prompts so it physically cannot "fix" things by editing the artifact it is judging. Same pattern as your spec-critic/pattern-critic.
- **Model choice**: use the strongest available model for stages 2, 4, 5 (synthesis and options); anything cheaper is fine for 6–9. Discovery synthesis on a 60-minute transcript can hit context limits — `ingest.py` should chunk by topic/time and the prompt should synthesize per chunk then merge, rather than one giant prompt.
- **No MCP servers needed for v1.** Filesystem + terminal cover everything. The only candidate later is a Graph MCP for calendar/Planner, and you've explicitly deferred that.

## 7. Shared tracker contract (with workflow #3)

`tracker/actions.xlsx`, sheet `Actions`, columns fixed:

`id | created | source | context | owner | action | due | urgency | effort | status | depends_on | notes`

(`context` = engagement name or export date; `urgency`/`effort` are filled by email triage and left blank by D2P. `scripts/tracker_init.py` creates the file; `scripts/append_tasks.py` ships with the workspace and is tested — see `scripts/README.md`.)

- `id` = short hash of (source:context, action) — dedup key.
- `source` = `d2p`, `meeting-notes`, `email-triage` or `one-on-one` so filtering is trivial.
- `append_tasks.py` is stdlib: unzip, append `<row>` elements to `xl/worksheets/sheet1.xml` using inline strings (`t="inlineStr"`, so `sharedStrings.xml` is never touched), bump the `<dimension ref>`, and if the sheet is an Excel Table also bump the `ref` in `xl/tables/table1.xml`. Existing rows, styles and column widths are bytes we never rewrite. Keep the tracker deliberately simple: one sheet, no formulas in data rows, no merged cells. If the file is locked (open in Excel), it writes `tasks.pending.csv` next to it and tells you; the next run drains it.
- Honest caveat: an xlsx appender with no library is the one script here that needs real testing against *your* tracker file, because Excel is stricter about workbook XML than PowerPoint is about slides. If it fights you, fall back to the tracker being a `.csv` that Excel opens — workflow #3 doesn't need xlsx internals either.

## 8. What I'd build first (and what I would not)

Build order, each step usable on its own:

1. `new_engagement.py`, `ingest.py`, `validate.py`, `status.py` + prompts for stages 1–3. Use it on your next discovery meeting. This alone removes the "write-up + follow-up prep" cost.
2. `ooxml.py` + `inspect_components.py` + `build_deck.py` with 3 component kinds (title, section, bullets) + `/outline-deck`. First real deck.
3. The rest of the component kinds, `lint_deck.py`, `storyboard.py`, speech/timing.
4. Options + proposal prompts + critic agent.
5. Team brief + `extract-tasks` + `append_tasks.py`.

Things I'd push back on:

- **Don't start with the deck.** It's the most satisfying part and the least valuable per hour saved; discovery synthesis and follow-up prep are where your time actually goes.
- **Don't try to make the AI infer the corporate style from screenshots or "look at these decks".** Approach D fails slowly and expensively. Cloning your own slides is exact and takes an afternoon.
- **Don't hand-author slide XML** (approach B) to "support any layout". Every slide kind you need is already a slide in a past deck; clone it.
- **Don't build a rail/orchestrator.** Nine stages and five gates fit in `status.py`. If you later merge workflows #1 and #3 into one tool, revisit.

## 9. Open questions to settle before implementation

1. Transcript `.md` shape — one sample (names redacted) so `ingest.py` normalizes speaker/timestamp lines correctly instead of guessing.
2. PDFs as discovery inputs: acceptable to convert them via Word (open PDF → save as .docx) before dropping into `inputs/`? Stdlib PDF text extraction works for simple office-generated PDFs and fails on the rest; I'd rather not pretend otherwise.
3. Your speaking pace (words/min) — measure once from a past recording so `timing.py` isn't guessing.
4. Is inline `powershell -Command "..."` also blocked, or only `.ps1` files? If inline works, Office COM gives slide PNG previews and a trivially safe Excel append; worth a 30-second test.
5. Does workflow #3's tracker already exist with a schema, or do we define §7 now and #3 adopts it?
